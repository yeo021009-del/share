> 사진 1장 → **내 차 기준** 주차 가능 판정 🟢🟡🔴

빈 갓길 자리 앞에서 사진을 한 장 찍으면, 내 차 제원으로 그 자리에 들어가는지 판정한다.

### 번호판 블러 스위치 (036 §A)

`PLATE_BLUR=on` 일 때만 결과 사진에 번호판 블러가 걸린다. **기본값은 `off`** —
띠 블러가 차량을 통째로 뭉개 시연에서 무엇을 찍은 사진인지조차 안 보였다.
코드는 그대로라 켜면 예전과 픽셀 단위로 같다. 감사 도구
`tools/blur_audit.py` 는 `overlay.blur_plates` 를 직접 부르므로 스위치와
무관하게 늘 블러를 검사한다.

## 5분 안에 띄우기

전제: Python 3.10+ 와 인터넷. GPU 는 **없어도 된다**(CPU 로 느리게 동작).

```bash
# 1) 설치
pip install -r backend/requirements.txt

# 2) 모델 내려받기 (최초 1회, 합계 ~500MB) — 현장 와이파이를 믿지 말고 미리 받아둘 것
python -c "from ultralytics import YOLO; YOLO('yolov8n.pt')"
python -c "from backend import pipeline; pipeline.get_depth_model()"

# 3) 서버 기동 — API 와 프론트를 한 주소에서 함께 서빙한다
uvicorn backend.main:app --host 0.0.0.0 --port 8000
#    → http://localhost:8000/            앱
#    → http://localhost:8000/analyze     API
```

Windows 라면 **`parkfit.bat` 더블클릭** 한 번으로 서버 기동 + 브라우저 열기까지 된다.

> `get_depth_model()` 로 받는 이유: Metric3D 는 그냥 `torch.hub.load` 하면
> **legacy mmcv import 때문에 실패한다.** 이 함수가 우회까지 처리한다 (아래 참고).

기동 확인:

```bash
curl http://localhost:8000/health
# {"ok":true,"version":"1.0.0","heic":true,"device":"cpu","metric3d_mmcv_shim":true}
curl http://localhost:8000/cars | head     # 차량 64종
```

`device` 로 GPU/CPU 를, `metric3d_mmcv_shim` 으로 우회 활성 여부를 바로 확인할 수 있다.

## 폰에서 쓰기

프론트가 서버와 **같은 출처**라 주소 하나만 있으면 된다.

```bash
# 1) 서버 기동 (PC)
parkfit.bat                       # 또는 uvicorn backend.main:app --host 0.0.0.0 --port 8000

# 2) 외부 공개 (다른 창에서)
ngrok http 8000 --url <고정주소>   # 고정 주소가 없으면 그냥 ngrok http 8000

# 3) 폰 브라우저에서 그 주소로 접속
#    https://<ngrok주소>/            일반
#    https://<ngrok주소>/?debug=1    디버그 패널 + 수동 두 점 측정
```

카메라 접근에는 **https 가 필요**하다 — ngrok 주소를 쓰면 자동으로 해결된다.
PC 의 로컬 IP(`http://192.168.x.x:8000`)로도 접속되지만 http 라 카메라가 막힌다.

> ngrok 무료 플랜은 첫 요청에 경고 HTML 을 돌려준다. 프론트는 모든 API 호출에
> `ngrok-skip-browser-warning: true` 를 붙여 이를 우회한다.

### 프론트를 따로 배포한 경우

`?api=https://<서버주소>` 로 다른 서버를 가리킬 수 있다. `?api=` 를 **빈 값**으로 주면
(`?api=`) 서버를 쓰지 않고 `demo_cache/` 의 사전 분석 결과로 동작하며, 화면 하단에
**`사전 분석 결과`** 배지가 뜬다 (라이브인 척하지 않는다).

## API

### `GET /cars`
`backend/cars.json` 그대로. CORS 전체 허용.

### `POST /analyze` — `multipart/form-data`

| 필드 | 필수 | 설명 |
|---|---|---|
| `image` | ✓ | JPEG / HEIC |
| `car_id` | △ | `cars.json` 의 id (예: `hy-avante-cn7fl`) |
| `car_class` | △ | 차급 폴백 (예: `중형`) |
| `car_dims` | △ | 직접 입력 `{"L":4710,"W":1825,"WB":2720,"R":5.3}` |

`car_id` / `car_class` / `car_dims` 중 **하나는 필수**(우선순위도 이 순서).

```bash
curl -X POST http://localhost:8000/analyze \
  -F "image=@photos/IMG_0421.jpg" \
  -F "car_id=hy-avante-cn7fl"
```

성공 시 `gap_m`, `gap_conservative_m`, `min_required_m`, `margin_m`, `verdict`,
`fit_score`, `overlay_image`(base64 data URL) 등을 돌려준다.

간격은 **세 가지 기준**으로 동시에 잰다. 어느 것이 옳은지는 실측 대조 전이므로
**판정은 계속 `gap_m` 하나만 쓰고**, 나머지는 표시·비교 전용이다.

| 필드 | 뜻 | 색 |
|---|---|---|
| `gap_m` / `gap_endpoint_m` / `gap_contour_m` | 양쪽 차체 윤곽 사이 최단거리 — 모든 쌍의 **하위 5 퍼센타일**. 끝점 A/B 는 그 채택 쌍이다 | 초록 |
| `gap_face_m` | 두 차의 면끼리 수직거리 (사잇각 > 15° 거나 점이 뭉쳐 있으면 `null`) | 파랑 |

끝점을 따로 구하던 3단 로직(`seg_mask`/`depth_edge`/`box_corner`)은 계속 빗나가서
**윤곽 결과에서 파생**시키도록 통합했다. 그래서 정상 경로에서는 위 세 필드가 같은 값이고
`endpoint_method` 는 `contour_p5` 다. 마스크가 없을 때만 옛 3단 폴백을 쓰고, 그 사실은
`endpoint_method` 에 그대로 남는다.

세 값이 크게 벌어지면 그 자체가 "촬영 각도가 나쁘다"는 신호다 (프론트 표 마지막 행).
최솟값이 아니라 하위 5 퍼센타일을 쓰는 이유: 최솟값은 깊이 노이즈가 가장 크게 튄 점을
자동으로 골라 점이 많을수록 과소추정이 심해진다.

### 자를 하나로 — `gap_m` 은 **지면거리**다

`gap_m` = `√(ΔX² + ΔZ²)`. **판정도 줄자 대조도 이 값 하나만 쓴다.**
나머지는 전부 진단이고, **어느 것도 줄자와 비교하지 않는다.**

| 필드 | 뜻 | 쓰임 |
|---|---|---|
| `gap_m` | 지면 위 거리 `√(ΔX²+ΔZ²)` | **판정 · 줄자 대조** |
| `gap_3d_m` | 3D 직선거리 `√(ΔX²+ΔY²+ΔZ²)` | 진단 — `ΔY` 가 섞인다 |
| `gap_horizontal_m` | 화면 가로 성분 \|ΔX\| | 진단 — **각도에 따라 변한다** |
| `endpoint_dz_m` | 두 끝점의 깊이차 \|ΔZ\| | 진단 |
| `endpoint_dy_m` | 두 끝점의 상하차 \|ΔY\| | 진단 |

불변식: `gap_3d_m ≥ gap_m ≥ gap_horizontal_m`, `gap_m ≥ endpoint_dz_m`.

**왜 지면거리인가.** 차는 지면 위를 움직인다. 두 범퍼 끝의 높이 차이(실측 0.07~0.50 m)는
차가 들어가는지와 무관한데, 3D 거리는 그것을 섞어 넣어 간격을 부풀린다.

**왜 `gap_horizontal_m` 이 아닌가.** 줄자는 두 범퍼 사이 **물리적 거리**를 잰다 —
보는 각도와 무관하다. 가로 성분은 `간격 × cos θ` 라 비스듬하면 구조적으로 작다
(θ = 40° 면 참값의 77 %). **측정이 틀린 게 아니라 다른 값이다.**

이걸 놓쳐서 TICKET-18~27 의 정확도 숫자가 전부 `gap_horizontal_m` 위에서 나왔다.
정면 사진에서는 두 값이 거의 같아 20장 내내 안 드러나다가, 비스듬한 사진이 들어오자
"판정 구간에서 앱이 작동하지 않는다"는 잘못된 결론까지 갔다. 자를 바꾸자:

| 실측 25장 | 옛 자 (`gap_horizontal_m`) | 새 자 (`gap_m`) |
|---|---|---|
| MAE | 0.953 m | **0.451 m** |
| 편향 | −0.695 m (−14.5 %) | **−0.077 m (−2.6 %)** |
| 지점 MAE (12곳) | 0.538 m | **0.333 m** |

**각도 불변성은 정답이 없어도 시험된다.** 같은 자리를 0°~46° 로 찍었을 때 `gap_m` 의
폭은 `GROUND_VIEW_SPREAD_MAX_M`(0.6 m) 아래여야 한다 — 쌍 선택·깊이·끝점 중 무엇이
깨져도 이 폭이 먼저 벌어지므로, 줄자가 없는 사진에도 쓸 수 있는 유일한 검사다.

`debug` 에는 `f_px` / `cx` / `cy` / `image_w` / `image_h` / `boxes` / `endpoints` /
`endpoint_depth_m` / `patch_sigma_m`(끝점별 `[σa, σb]`) / `patch_sigma_max_m` 과
끝점 보정 정보(`endpoint_method` / `endpoint_clipped` / `endpoint_refine_steps` /
`mask_area_px`)와 측정 기준 근거(`contour_points` / `contour_pairs_used` /
`contour_endpoints` / `face_lines` / `face_angle_deg` / `measure_notes`)가 들어간다.

프론트에서 `?debug=1` 을 붙이면 결과 화면에 그대로 펼쳐 보여주고, **측정 결과 복사** 패널이
함께 뜬다 — 읽기 좋은 텍스트 블록과 스프레드시트용 TSV(헤더+값 1행) 두 가지로 복사된다.
줄자 실측값을 넣으면 오차·오차율까지 함께 담긴다.

`warnings` 는 **실패가 아닌 경고**다(항상 존재, 없으면 `[]`).

| code | 뜻 |
|---|---|
| `ENDPOINT_DEPTH_MISMATCH` | 두 끝점의 깊이차 > 1.0 m — 같은 주차선의 두 범퍼가 이만큼 어긋날 수 없다 |
| `LOW_MASK_FILL` | 마스크가 박스를 채우는 비율이 0.80 미만 — 실루엣이 차를 제대로 못 덮었다 |
| `SPARSE_CONTOUR` | 윤곽점이 30개 미만 — 하위 5% 채택이 통계적 의미를 잃는다 |
| `SPARSE_CONTOUR_LEFT` / `_RIGHT` | 위와 같되 **어느 쪽 차량**인지 (한쪽만 실패가 흔하다) |
| `CONTOUR_FALLBACK` | 정밀 경로가 실패해 거친 폴백으로 쟀다 — 대략값이다. **지금은 응답까지 오지 않는다**: 같은 조건이 수동 회부로 걸린다 |
| `HIGH_SIGMA` | 끝점 패치 σ 가 상한(0.15 m)을 넘었다 — 깊이 불연속에 걸쳐 있다 |
| `ENDPOINT_PROFILE_UNRELIABLE` | 끝점 깊이를 범퍼 면까지 되돌리지 못했다 |
| `DEPTH_BODY_FALLBACK` | 번짐 밖에 패치를 놓을 자리가 없어 실루엣 깊이 중앙값으로 쟀다 — 간격이 조금 과대해진다 |

이 경고들은 **신뢰도를 실제로 깎는다** (`debug.quality_factor`). 실측 3.2 m 자리를
4.3 m 로 잰 사진 두 장이 경고 하나 없이 64% / 61% 로 통과한 것이 이 장치를 만든
이유다 — 값을 못 고치더라도 못 믿을 사진이 조용히 통과하는 것은 먼저 막아야 한다.

**바깥쪽 프레임 잘림은 경고도 재촬영도 아니다.** 프레임에 걸리는 것은 두 차의
바깥쪽 끝이고 우리가 재는 것은 안쪽 모서리다. 빈 자리 앞에 서서 찍으면 양옆 차가
프레임을 넘어가는 것이 정상 촬영이고, 오차 분해에도 잘림 항이 없다(깊이 0.65 +
픽셀 0.25 + 배율 0.22 로 전부 설명된다). 실패 사진 두 장이 모두 잘려 있던 것은
**상관이지 인과가 아니었다.** 그 사실은 `debug.vehicle_partial` 에 진단으로만 남는다.

`mask_fill_ratio` 임계 0.80 은 **잠정값**이다 — 근거가 사진 두 장(0.69 / 0.795)뿐이라
경고까지만 하고 재촬영으로 올리지 않는다.

**재촬영 요청은 에러가 아니라 `200 OK` + `ok:false`** 다.

| code | 조건 |
|---|---|
| `DIGITAL_ZOOM` | EXIF `DigitalZoomRatio` > 1.05 |
| `NOT_ENOUGH_CARS` | 경계 차량 2대를 못 찾음 |
| `GAP_NOT_FOUND` | 좌우 박스 사이 유효 간격 없음 |
| `NO_VALID_PAIR` | 좌우 후보의 깊이가 크게 어긋나 **나란히 선 두 대**가 없음 |
| `DEPTH_UNRELIABLE` | 끝점 패치 σ > 0.6 m |
| `CLIPPED_VEHICLE` | **재려는 안쪽 모서리**가 프레임 밖 — 잴 지점 자체가 사진에 없다 |
| `NOT_PARALLEL` | 두 면의 사잇각 > 25° — 같은 자리를 감싸는 두 대가 아니다 |

경계 차량은 화면 x 좌표만으로 고르지 않는다 — 그러면 빈 자리 **뒤쪽**에 있는 무관한
차를 집어 간격이 부풀어 오른다(실측: 좌 15.72 m / 우 8.03 m → 9.53 m). 좌우 후보를
여럿 두고 조합마다 **깊이 유사도 + 화면 중앙 근접도**로 점수를 매긴다. 아래 조건에
걸리면 배제하고, 남는 조합이 없으면 억지로 고르지 않고 `NO_VALID_PAIR` 로 재촬영을
요청한다. 후보와 점수·배제 사유는 `debug.candidates` 에 남는다.

| 배제 | 조건 |
|---|---|
| `depth_diff` | 두 차의 앞뒤 깊이차가 `PAIR_DEPTH_DIFF_MAX_M` = 6 m 를 넘음 (평행주차 일반형 구획 길이) |
| `too_small` | 마스크(없으면 박스) 면적 < 이미지의 1% |
| `band_too_thin` | 범퍼 밴드에 들어온 행 < 60 |
| `size_mismatch` | 좌우 면적비 > 4배 |

깊이가 비슷해도 **크기가 크게 다르면** 한쪽이 훨씬 멀다는 뜻이다 — 길 건너 주차장 차
두 대를 재서 12.76 m 가 나온 사례가 깊이 조건만으로는 통과했다.

### 신뢰도의 경로 계수

정밀 경로(윤곽 하위 5%)가 실패해 폴백으로 내려갔는데 σ 만 보고 높은 점수를 주면
사용자는 대략값을 정밀값으로 믿는다. `fit_score` 에 경로 계수를 곱한다.

| `endpoint_method` | 계수 |
|---|---|
| `contour_p5` | 1.0 |
| `seg_mask` | 0.6 |
| `depth_edge` | 0.5 |
| `box_corner` / `contour_p5_boxfallback` | 0.4 |

폴백이면 `warnings` 에 `CONTOUR_FALLBACK` 이 실리고 — 그리고 **응답까지 가지 않는다.**
아래 회부를 참고.

### 값을 낼 수 없으면 값을 내지 않는다 — 수동 회부

깊이 비 게이트를 미터 게이트로 바꾸자(TICKET-25) 막혀 있던 사진 5장 중 4장이
**틀린 값**으로 바뀌었다 (+2.66 / −2.97 / −2.94 / −2.49 m). 거절과 오답은 같은 실패가
아니다 — 거절은 사용자가 다시 찍게 하지만, **틀린 값은 그대로 믿게 만든다.** 그래서
"값 없음" 과 "값 있음" 사이에 **회부**를 뒀다: 자동 측정을 포기하고 사람이 두 점을
찍게 넘긴다. 회부되면 **값을 아예 싣지 않는다** — 화면에 숫자가 보이면 사용자는
숫자를 믿지 옆의 신뢰도를 읽지 않는다.

응답은 재촬영과 같은 `200 OK` + `ok:false` 이고, `refer_manual: true` 와
`measure_token` 이 함께 온다. `gap_m` · `verdict` · `fit_score` 는 **없다.**

| code | 조건 | 근거 |
|---|---|---|
| `DZ_CONTRADICTS_GATE` | 끝점 Δz > 6 m | 쌍을 통과시킨 게이트를 결과가 도로 위반했다. 둘 중 하나가 틀렸고 **어느 쪽인지 모른다** |
| `CONTOUR_FAILED` | `endpoint_method != contour_p5` | 박스 모서리·실루엣 극점으로 내려간 대략값이다 |

**넣지 않은 신호 셋** — 셋 다 근거가 없어서 뺐지, 결과가 나빠서 뺀 게 아니다.

- **최대편차(spread)**: TICKET-23 §C 에서 실측으로 기각됐다.
- **카메라 근접 차**: 26 mm 상당이면 HFOV 69.4°, 깊이 `z` 에서 프레임 가로 실폭은
  `1.385·z` 다. 차가 가장 좁게 보이는 정면(폭 1.8 m)조차 `z ≥ 1.30 m` 면 프레임에
  들어간다 — 광학만으로 세울 수 있는 근접 하한은 **1.30 m** 이고, 실제로 문제를 일으킨
  **1.93 m 차를 못 거른다.** 관측값에 맞춰 임계를 올리면 그건 광학이 아니라 그 사진에
  맞춘 숫자다. 그래서 안 쓴다.
- **`DEPTH_DOMINATES_GAP` (Δz > Δx)**: TICKET-28 §C-2 에서 **철회**. 논거는 "답의
  절반 이상을 약한 채널이 내면 못 믿는다" 였는데, 이 조건이 회부한 세 장(θ 58~67°)의
  지면거리는 줄자 4.80 대비 **−0.21 / −0.45 / −0.45 로 거의 맞았다.** 즉 맞는 값을
  버렸고, 정작 진짜 오답(+2.77)은 θ 10° 라 걸리지도 않았다. **깊이가 많이 쓰였다는
  것과 답이 틀렸다는 것은 별개다.** 되밀기(TICKET-21)와 같은 사유 — 전제가 반박됐다.

`manual_referral()` 은 **`dx_m` 을 인자로 받지 않는다.** 받을 수 있으면 `Δz > Δx`
류가 조용히 되살아나기 때문이고, 테스트가 그 시그니처를 고정하고 있다.

### 수동 두 점 측정 (`POST /measure`)

두 가지 일을 한다.

1. **회부된 사진의 출구.** 차종을 함께 주면 자동과 **같은 판정 함수**(`geometry.evaluate`)
   로 🟢🟡🔴 까지 낸다. 회부해 놓고 여기서 판정이 안 나오면 회부는 막다른 길이다.
2. **검증 도구.** 값이 틀렸을 때 **끝점이 틀린 건지 깊이가 틀린 건지** 갈라 본다.
   차종을 안 주면 예전처럼 거리만 낸다.

수동이라고 관대하게 봐 주지 않는다. 수동 점은 실루엣이 없어 **번짐 밖으로 걸어 나가지
못하고** 찍힌 자리의 패치 중앙값을 그대로 쓰므로, 경로 계수는 깊이 폴백과 같은
`0.7` 이다. σ 가 크면 `s_edge` 도 그만큼 떨어진다.

`POST /analyze` 에 `measure=1` 을 넣으면 응답에 `measure_token` 이 실린다. **회부·재촬영
때는 요청하지 않아도** 토큰이 나온다 — 값을 못 내보내는 경우엔 수동이 유일한 출구라서다.
(다만 차를 한 대도 못 찾으면 깊이 추론 **전에** 끝나므로 토큰이 없다. 의도한 비용 절약이다.)
서버는 깊이맵과 카메라 파라미터만 **최대 10분 / 5건**(LRU) 들고 있다 — **원본 사진은
보관하지 않는다**. 만료되면 `410` 이다.

```bash
curl -X POST http://localhost:8000/measure -H "Content-Type: application/json" \
  -d '{"measure_token":"...","points":[[1160,1352],[2840,1352]],"car_id":"hy-avante-cn7fl"}'
```

응답의 `distance_ground_m` 이 판정·줄자 대조 기준이다. `distance_3d_m` 과
`distance_horizontal_m` 도 함께 오지만 **진단 전용**이다 (위 "자를 하나로" 참고).

프론트는 결과 사진을 두 번 눌러 재고, `실제 길이 (m)` 를 넣으면 비율·오차를 바로
보여준다. 주차선 한 칸(2.5 m)처럼 **크기를 아는 물체**로 재면 깊이 스케일이 맞는지
확인할 수 있다. 표시 크기와 원본 해상도가 다르므로 클릭 좌표는 `object-fit:contain`
배율로 원본 좌표계에 되돌려 전송한다. 회부되면 측정 모드가 **켜진 채로** 열려서
사진의 두 지점만 누르면 된다.

## 어떻게 재는가

```
EXIF → f_px = f35 × W_px / 36
  ↓  YOLOv8-seg 로 경계 차량 2대 (중심선 기준 좌/우 가장 안쪽)
  ↓  Metric3D v2 → 픽셀별 metric depth (m)
  ↓  윤곽점 = 마스크 45~80% 높이의 안쪽 최외곽 (범퍼~휠하우스 상단)
  ↓  깊이는 **프로파일이 평평해지는 첫 지점**에서 15×15 중앙값 (칸수는 사진마다 다름)
  ↓  끝점이 평평해지지 않으면 실루엣 깊이 중앙값으로 폴백 (경고 + 경로 계수↓)
  ↓  윤곽점은 폴백 없이 **버린다** — 한 값으로 몰리면 점구름이 망가진다
  ↓  σ > 0.5 m 는 버린다 (경계 걸침 신호 — 깊이가 맞는지는 σ 로 알 수 없다)
  ↓  깊이 이상치 제거 (MAD 기반)
  ↓  전면 필터: 가장 튀어나온 x 에서 폭의 6% 안쪽까지 (점이 30개 미만이면 20% 까지 확장)
  ↓  X=(u−cx)Z/f_px, Y=(v−cy)Z/f_px → 모든 쌍 거리의 **σ 가중 하위 5%** = gap, A/B
```

**패치를 윤곽점 바로 위에 두면 안 된다.** 절반이 배경이라 중앙값이 차와 배경 사이로
끌려가고 σ 가 0.4 m 까지 뛴다(오차 +0.75 m). 재는 **좌표는 범퍼 면 그대로** 두고
**깊이만** 안쪽에서 읽는다. 밀어 넣은 자리에서 패치가 **통째로** 실루엣 안에 들어가는지
확인하고, 안 되면 그 점은 버린다 — 사이드미러 같은 얇은 돌출부는 8 px 만 들어가도 이미
배경이라 확인 없이 재면 안쪽 샘플링이 아무 효과가 없다.

```

### 가드가 가짜였던 날 — 2026-08-25 (TICKET-015 §A)

**검사를 만들었는데, 그 검사가 고장난 코드를 통과시켰다.**

`/analyze` 가 `async def` 인데 그 안에서 6.6초짜리 동기 함수를 그대로 불러
이벤트 루프를 잡고 있었다. 한 명이 분석하는 동안 다른 사람은 **앱 화면조차
열리지 않는다.** 고치고(`run_in_threadpool` + 동시 1건 제한), 두 개의 검사를
붙였다. 둘 다 통과했다.

그 다음에 한 일이 이 기록의 요점이다 — **일부러 옛 코드로 되돌려 봤다.**

```
result = pipeline.analyze(...)      # 옛 블로킹 호출로 복원
pytest -k AnalyzeDoesNotBlock  →  7 passed     ← 잡아야 할 것을 못 잡았다

두 검사가 각각 다른 이유로 틀렸다.

| 검사 | 무엇이 틀렸나 |
|---|---|
| "분석 중에 `/health` 가 빨리 답하나" | 대기 시간을 `anyio.sleep` **뒤에서** 쟀다. 루프가 막히면 **그 sleep 자체가 안 돌아서** 기다린 시간이 통째로 빠진다. 막힌 코드에서도 "빨랐다" 로 나온다 |

고친 방법:

- 시작 시각을 **task group 밖에서** 잡아 "분석 시작 후 몇 초에 답했나" 를 잰다
- 루프 스레드 id 를 **실행 중에** 알아내 작업 스레드 id 와 비교한다

고친 뒤 다시 되돌려 보니 둘 다 실패했다 —
`분석 시작 1.27s 뒤에야 /health 가 답했다`. 그제야 진짜 가드가 됐다.

```
· 검사를 만들면 **고장난 코드로 되돌려 실패를 확인**한다. 통과만 보면 모른다
· 시간을 재는 검사는 **막힌 쪽에서도 그 코드가 도는지** 먼저 따진다
· "무엇이 아니다" 로 비교하지 말고 **비교 대상을 실행 중에 알아낸다**
```

이 프로젝트에서 같은 종류의 사고가 세 번째다 (TICKET-002 돌연변이 검사,
TICKET-009 문서-코드 불일치, 그리고 이번). 앞의 둘은 **검사가 약한 것**을
찾았고, 이번은 **검사가 아예 반대로 도는 것**을 찾았다.

### 어두운 사진을 축소한 그림으로 판정하지 않는다 (TICKET-004 §C 철회)

004 §C 는 야간 사진 두 장(`IMG_1293`·`IMG_1294`)에서 끝점을 손으로 179 px·166 px
옮겼더니 오차가 −14.3 % → −3.8 %, −12.5 % → −2.2 % 로 줄었다고 적었다. 예측을
먼저 쓰고 그대로 맞았으므로 **원인을 잡았다고 판단했고, 그 위에 TICKET-007 을 세웠다.**

007 을 구현하기 전에 §B 가 요구한 확인 — "마스크가 정말 그늘을 물었는지 그림으로
본다" — 을 하자 반대가 나왔다. 감마·CLAHE 로 밝기를 편 원본에서 마스크 경계는
범퍼 앞면에 **정확히** 붙어 있었고, 내가 손으로 찍은 자리는 범퍼보다 한참 **안쪽**,
차체 위였다.

무슨 일이 있었나: 004 §A 는 가로 1400 px 로 줄인 오버레이를 봤다. 야간 사진에서
어두운 범퍼 앞부분이 그 축소본에서 배경과 구분되지 않아, 차가 실제보다 오른쪽에서
시작하는 것으로 보였다. 점을 안쪽으로 밀면 간격이 늘어나는데 **그 사진들이 마침
과소 측정이어서** 숫자가 좋아졌다. 맞는 방향으로 움직인 것이 원인을 맞혔다는 뜻은
아니다.

```
· 어두운 사진은 **밝기를 펴서** 본다. 안 그러면 경계를 눈으로 못 잡는다
· 끝점을 눈으로 판정할 때는 **원본 배율**로 본다. 축소본은 어두운 경계를 지운다
· "손으로 고치니 좋아졌다" 는 **원인의 증거가 아니다** — 오차를 줄이는 방향은
  대개 여러 개고, 그중 하나가 우연히 맞을 수 있다
```

`IMG_1293` 의 남은 −14 % 는 끝점이 아니라 **깊이**에서 온다: 같은 픽셀로 줄자
3.10 m 가 나오려면 깊이가 5.63 → 6.58 m 여야 한다(+17 %). TICKET-005 가 번호판으로
잰 두 대에서 AI 깊이가 8~12 % **과소**였던 것과 방향이 같다.

### 지렛대 — 어느 값이 흔들릴 때 답이 무너지는가

지면거리를 두 끝점의 픽셀·깊이로 미분하면, 그 사진에서 **무엇이 답을 쥐고 있는지**가
숫자로 나온다 (`debug.gap_sensitivity`, `pipeline.gap_sensitivity`):

```
∂gap/∂z_a = ( Δx·m_a + Δz) / gap        m = (u − cx)/f,  Δx·Δz 는 부호 있는 값
∂gap/∂z_b = (−Δx·m_b − Δz) / gap
```

**두 끝점의 지렛대가 크게 다를 수 있다.** 한쪽은 좌우 성분과 앞뒤 성분이 더해지고,
다른 쪽은 상쇄된다. `IMG_1307` 은 0.729 대 −0.113 으로 **6.4배** 차이였고, 그 지렛대에
깊이 보정 −1.00 m 가 곱해져 간격이 −0.86 m 움직였다 (예측 −0.76).

### 오차의 범인은 번짐도 잡음도 아니다

실측 25장에서 각 항의 크기(출시 경로):

| 항 | 중앙 |
|---|---|
| 끝점 픽셀 10칸 | 0.021 m |
| 깊이 패치 σ 효과 | 0.041 m |
| 평면 보정이 만든 이동 | 0.128 m |
| **실제 오차** | **0.265 m** |

**끝점이 10 px 틀려도 0.02 m 다** — 실제 오차의 8 % 크기다. TICKET-13·15 이후 여러
티켓이 기대 온 "가장자리 번짐 때문에 못 잰다" 는 서사는 **적어도 이 사진들에서는
주된 원인이 아니다.** 깊이 **잡음**도 아니다(σ 효과가 오차의 6분의 1).
남는 것은 **깊이의 계통 오차**이고, 지금 있는 어떤 지표도 그것을 재지 못한다.

그리고 **민감도는 정확도가 아니다.** 지렛대는 답이 얼마나 *움직이는지* 를 거의
완벽히 예측하지만(r = 0.995), 그 움직임이 정답 쪽인지 반대쪽인지는 예측하지
못한다 — 지렛대가 큰 사진이 실제로 더 틀리지도 않았다 (TICKET-34 §C-2 기각).
그래서 지렛대로 사진을 거르지 않는다.

### 리포트 숫자는 **어느 설정에서 나왔는지**와 함께 다녀야 한다

하니스는 경로를 여러 개 돌린다(`walk` / `plane`, 그리고 좌우 반전). 출시 설정은
그중 **하나**다. TICKET-28 §G-3 이 리포트의 `off` 행으로 정확도를 보고했는데
출시는 `on` 이었다 — 판정 구간 통과가 6/10 이 아니라 **4/10** 이었다.

`path_mode == "off"` 라는 문자열이 요약 코드에 박혀 있었고, TICKET-25 에서
`USE_BODY_PLANE` 을 승격한 뒤에도 그 문자열이 안 바뀐 것이다. **자 사건과 같은
병이다** — 코드 한 곳이 바뀌었는데 그것을 읽는 다른 곳이 안 따라갔다.

지금은 이렇게 막는다:

```
· 리포트 모든 행에 설정 스탬프 (use_body_plane · safety_margin_m · code_sha)
· 출시 설정이 아닌 행은 path_mode 에 _alt 접미사가 붙는다
· 요약은 반드시 release_rows() 를 거친다 — 경로 이름을 문자열로 박으면 테스트가 깨진다
· 행의 스탬프가 지금 코드와 다르면 요약이 **거부**된다 (옛 리포트를 새 코드로 요약 금지)
```

### 집계 하나만 보면 결론이 갈린다

같은 자리를 여러 각도에서 찍은 묶음을 표본 1로 줄이는 방법이 둘인데, **둘이
다른 답을 낸다.**

| 집계 | 뜻 | 판정 구간 `spotC`(plane) |
|---|---|---|
| `\|묶음 평균오차\|` | 그 자리에서 **치우쳐** 있는가 | 0.022 |
| `묶음 \|오차\| 평균` | 그 자리에서 **한 장** 찍으면 얼마나 틀리는가 | 0.314 |

**14배 갈린다.** spotC 의 오차가 −0.46 / +0.26 / +0.46 / +0.12 / −0.27 로 흩어져
상쇄되기 때문이다. 앞의 집계만 보면 "거의 정확" 으로 읽는다. 사용자는 다섯 장이
아니라 **한 장**을 찍는다.

같은 병이 편향에도 있다: 25장 오차의 평균은 −0.083 인데 **중앙값은 −0.231** 이다.
`IMG_0336` 한 장(+2.77)이 평균을 끌어올린 것이다. 그래서 이제 요약은
**평균과 중앙값을 같이 내고**, 둘이 갈리면 경고를 찍는다. 지점 MAE 도 두 집계를
같이 내고, 1위가 갈리면 경고한다.

### "미정" 은 만료 기한이 있어야 한다

`GapBreakdown` 의 원래 주석은 이랬다:

> 어느 쪽이 판정 기준으로 옳은지는 **아직 확정되지 않았으므로** 둘 다 보여주기만 하고
> 판정은 건드리지 않는다.

미결로 남겨 둔 것이 시간이 지나며 **확정된 것처럼 쓰였다.** README 와 하니스가
`gap_horizontal_m` 을 대조값으로 굳혔고, 아무도 그 문장으로 돌아가지 않았다.
그 사이에 나온 정확도 숫자가 **전부 잘못된 자 위에 있었다.**

미정을 적을 때는 **누가 언제 무엇을 보고 닫을지**를 함께 적는다. 못 적겠으면
그건 미정이 아니라 **결정을 미룬 것**이고, 미룬 결정은 조용히 굳는다.

### 깊이는 **차체 평면과 시선의 교점**으로 구한다

경계에서 안쪽으로 걸어가며 프로파일 모양을 보는 접근은 **번짐 ramp 와 진짜 비스듬한
면을 구분할 수 없다.** 둘 다 "경계가 멀고 안쪽으로 갈수록 몸통 중앙값에 수렴" 인데,
정면 차에서는 그 수렴값이 정답이고 비스듬한 차에서는 1.15 m 오답이다. 모양만으로는
가를 정보가 없다.

그래서 ramp 구간을 **아예 보지 않는다.** 번짐이 절대 닿지 않는 차 **내부**만
샘플링(실루엣을 ViT 패치 2칸만큼 침식)해 X–Z 평면에 직선을 맞추고, 실루엣 픽셀의
시선과 그 직선을 교차시킨다.

```
시선 :  X = m·Z              (m = (u_edge − cx) / f)
차체 :  (X, Z) = (x0, z0) + t·(dx, dz)

t = (m·z0 − x0) / (dx − m·dz)     →   Z_edge = z0 + t·dz
```

정면 차는 차체 직선이 시선축에 수직이라 `dz = 0` → `Z_edge = z0` 로 **정확히 몸통
깊이**가 된다. 비스듬한 차는 `dz ≠ 0` 이라 교점이 자동으로 먼 모서리로 간다.
**각도별 분기도, 번짐 상수도, 걷기도 없다.**

내부 점은 픽셀과 깊이가 **같은 지점**을 가리키므로 방향 추정이 왜곡되지 않는다 —
"범퍼 픽셀 + 안쪽 깊이" 조합이 안고 있던 불일치가 사라진다.

교점을 못 쓰는 경우(시선이 차체와 나란함 · 비물리적 Z · 내부 점 부족)는 걷기 경로로
떨어지고 사유가 `debug.body_plane.status` 와 `contour_profile.plane_gates` 에 남는다.

**알려진 한계**: 차는 평면이 아니다. 앞면과 옆면을 함께 보이는 차는 직선 하나로
안 맞고, 그 평균 방향을 실루엣까지 외삽하면 오차가 커진다. 정면 3장에서 이 영향이
MAE 0.132 → 0.196 이었다. 비스듬한 표본이 모이면 어느 쪽이 이득인지 갈린다.

### 깊이 모델은 원본을 보지 않는다 — 경계 번짐 (폴백 경로)

이게 지금 남은 오차의 **주 원인**이다.

```
원본 4032 × 3024
   ↓ scale = min(616/3024, 1064/4032) = 0.2037
모델 입력 821 × 616
   ↓ ViT 패치 14 px
패치 1개 = 원본 69 px
```

경계에 걸친 패치는 차와 배경을 한 값으로 뭉갠다. 배경이 훨씬 머니까 그 패치는
**멀게** 나오고, 우리가 재려는 범퍼 모서리가 정확히 그 자리다. 그래서 좌표(방향)는
범퍼 픽셀 그대로 두고, **깊이(거리)만** 번짐 밖에서 읽어 그 픽셀에 적용한다.

```
X = (u_범퍼 − cx) · Z_안쪽 / f
     ▲ 범퍼 픽셀 그대로       ▲ 번짐 밖에서 읽은 깊이
```

**안쪽으로 들어간 거리는 답에 등장하지 않는다** — 빼야 할 보정값이 없다. 빼야 할
상수가 남아 있다면 아직 번짐 안에서 읽고 있다는 뜻이다.

들어가는 거리는 `blur_inset_px()` 가 `METRIC3D_INPUT_SIZE` 와 ViT 패치 크기에서
**계산한다**. 미터 상수로 박으면 가까운 차는 과하게, 먼 차는 모자라게 들어간다.

**몇 칸 들어갈지는 상수가 아니다.** 처음에는 "ViT 패치 2개면 벗어난다" 고 구조에서
유도했는데, 실측 프로파일은 2칸에서 아직 차체 중앙값보다 +0.23~+0.51 m 높고
**4칸 부근**에서야 평평해졌다. 전역 어텐션과 디코더 업샘플까지 더해지면 유효 번짐
폭에 닫힌 형태가 없다 — **구조에서 상수를 유도하려던 접근 자체가 성립하지 않았다.**

그렇다고 4·5·6 중 하나를 박으면 사진 세 장에 대한 과적합이다. 그래서 그래프에서
실제로 본 것 — **"어느 지점부터 값이 안 변한다"** — 을 그대로 규칙으로 만들었다.

```
경계에서 한 칸(ViT 패치 하나)씩 안으로 들어가며 깊이를 읽는다
    ↓  직전 칸과의 차이가 임계 미만이면 → 그 자리를 채택 (첫 번째 평평한 지점)
    ↓  탐색 상한(12칸)까지 안 평평하면 → 실루엣 깊이 중앙값으로 폴백 + 경고
```

임계는 깊이 차이(m)가 아니라 **그 차이가 간격에 미치는 영향(m)** 이다 —
`X = (u−cx)·Z/f` 이므로 같은 ΔZ 도 화면 가장자리일수록 X 를 크게 흔든다.
이 규칙에는 거리·카메라·모델에 대한 가정이 없다. **사진마다 스스로 찾는다.**
실제로 채택된 칸수는 사진·차량마다 6~10 칸으로 달랐고, `debug` 에 남는다.

**현재 정확도** (실측 3장): +0.03 / +0.04 / **+0.32**, MAE **0.131**.
두 장은 ±0.05 로 들어왔고 IMG_1280 한 장만 남았다. 끝점 깊이는 이제 차체 대표보다
**앞**에 있다(−0.02~−0.11) — 범퍼가 차 중심보다 뒤일 수 없다는 조건을 만족한다.

σ 는 이 오차를 **못 잡는다**. 번짐 구간은 한 패치 안에서 값이 균일해 σ 가 0.02 까지
작아지는데 깊이는 0.4 m 틀린다 — **σ 는 "매끈한가" 이지 "맞는가" 가 아니다.**

### 안쪽에서 읽되, 읽은 값을 그대로 쓰지는 않는다

안쪽에서 읽는 것 자체는 맞다. 틀린 것은 **읽은 값을 그 점의 깊이인 것처럼 쓰는 것**
이었다. 차체는 안쪽으로 갈수록 물러나므로 그만큼 끝점이 뒤로 밀린다. 실측에서 끝점
깊이가 차체 대표보다 `+1.13 / +0.87 m` 더 멀게 나온 원인이 이것이고, 끝점이 가로로도
깊이로도 멀어져 **실측 3.2 m 자리가 4.30 / 4.32 m** 로 잡혔다(배율 1.34~1.35).

```
      ┌──────────────────────
      │  ✕   ✕   ✕   ✕      안쪽 네 지점의 깊이 z(d)
      │ ●                    d = 경계에서 안쪽으로 들어간 거리 (m)
      └──────────────────────
      z │           ✕
        │        ✕           z = a + b·d 로 적합
        │     ✕
        │  ✕
        │●  ← 끝점 깊이 = a  (d = 0)
        └────────────── d
```

표본 간격은 **미터 기준**이다. 픽셀로 고정하면 가까운 차는 조금, 먼 차는 많이 밀려
거리마다 편향의 크기가 달라진다(실측에서 39~113 px 로 들쭉날쭉했다). 표본 지점이
전부 몸통 안쪽이라 패치도 깨끗하다 — 노이즈 회피와 정확도를 동시에 가져간다.

패치는 반올림된 픽셀에 놓이므로, 요청한 `d` 가 아니라 **실제로 읽은 자리**를 적어
양자화 편향을 없앤다. 표본은 하위 백분위가 아니라 **중앙값**으로 읽는다 — 패치가
통째로 몸통 위에 있으므로 그 자리의 깊이를 정확히 알아야 직선이 맞는다.

**기울기 `b` 가 공짜 검사기다.** σ 하나로만 판단하던 때는 "왜 이상한지"를 알 수 없었다.

| `b` | 뜻 | 조치 |
|---|---|---|
| 양수, 완만 | 정상 (안쪽 = 멀어짐) | 채택 |
| 음수 (< −0.30) | 몸통이 아니다 — 배경이나 다른 물체 | 버린다 |
| 과대 (> 15 m/m) | 경계에 걸쳤거나 사이드미러 같은 얇은 돌출부 | 버린다 |
| 잔차 RMS > 0.10 m | 한 면 위가 아니다 | 버린다 |

적합 불량 판정에 R² 를 쓰지 않는 이유: 차를 정면에서 보면 참 기울기가 0 이라 R² 가
0/0 이 된다. 잔차 RMS(m)는 어느 각도에서든 뜻이 있다.

σ 상한은 **채택되는 점**에만 건다(0.15 m). 밴드 전체에는 느슨한 0.5 m 만 적용한다 —
그 점집합은 면 직선 피팅에도 쓰이는데, 직선 피팅은 점이 많을수록 안정적이라 미리
잘라내면 면이 보는 구간이 좁아져 다른 편향이 생긴다.

진단은 `debug.endpoint_profile`(끝점별 상태·기울기·잔차·표본 수·재샘플링 횟수)과
`debug.contour_profile`(차량별로 몇 개를 왜 버렸는지)에 남는다.

**전면 띠도 고정이면 안 된다.** 차가 비스듬하면 그 면이 화면에서 대각선이라 6% 띠에는
점이 거의 안 들어온다(실측: 마스크 731,108 px 인데 통과 점 8개). 점이 30개에 못 미치면
6% → 10% → 14% → 20% 로 넓혀 재시도하고, 실제로 쓴 폭을 `debug.front_band_px` 에 남긴다.

σ 0.5 초과만 버리면 σ 0.2 와 0.45 를 같은 무게로 취급하게 되므로, 쌍마다 두 점의
가중치 `max(0.02, 1 − σ/0.5)` 를 곱해 **가중 퍼센타일**을 쓴다.

**끝점을 박스 모서리로 잡으면 안 된다.** 차가 비스듬하면 그 좌표에 차가 없고 그 뒤
지면이 있어서, 지면 깊이가 끝점 깊이로 들어온다(실측: 두 끝점 깊이차 1.47 m).
세로 구간도 45~80% 로 좁혀야 한다 — 아래쪽은 차 밑 그림자·언더바디라 범퍼보다 안쪽에
있어서 선이 차 위로 올라탄다.

| `endpoint_method` | 방법 |
|---|---|
| `contour_p5` | 세그 실루엣의 윤곽 최단거리 쌍 (정상 경로) |
| `contour_p5_boxfallback` | 마스크가 없어 **박스 사각형**을 실루엣으로 쓴 경우 |
| `depth_edge` | 윤곽점이 부족할 때 — 깊이가 0.3 m 이상 튀는 첫 지점 |
| `box_corner` | 최후 폴백 — 박스 하단에서 8% 위 |

### 마스크가 실제로 쓰였는지 어떻게 아는가

`mask_source` 는 **받았는지**, `contour_source` 는 **썼는지** 다. 둘은 다르다 —
폴리곤이 와도 래스터화가 비거나 사실상 사각형이면 윤곽이 테두리를 따라간다.

| 필드 | 뜻 |
|---|---|
| `mask_source` | `seg` / `box_fallback` — 마스크를 받았는가 (요청마다) |
| `contour_source` | 차량별 `mask` / `box` — 윤곽이 실제로 쓴 소스 |
| `mask_rejected` | 폴리곤이 박스와 안 맞아 버려졌는가 |
| `mask_fill_ratio` | 실루엣이 박스를 채우는 비율 |
| `contour_edge_span_px` | 밴드 안에서 안쪽 변이 움직인 폭 — **0 이면 사각 테두리** |
| `endpoint_offset_px` | 끝점과 박스 변의 거리 — **0 이면 테두리를 짚은 것** |
| `mask_raster` | 마스크가 만들어진 해상도 |

세그 폴리곤은 박스와의 겹침으로 좌표계를 검증하고, 추론 해상도 좌표면 원본으로
스케일한다(못 맞추면 버리고 경고). 마스크는 `retina_masks=True` 로 **원본 해상도**로
받는다 — 기본값(160×160)이면 4000px 사진에서 셀 하나가 25 px 라, 45~80% 밴드 안에서
가장자리가 직선으로 양자화돼 박스 변과 구분되지 않는다.

판정 (`backend/geometry.py`):

```
l₁      = (L − WB) × (0.52 if SUV else 0.55)
L_min1  = √(2RW + (L − l₁)²)            1회 진입 최소 길이
L_prac  = min(L + 0.8, L_min1)          다회 전환 실용 하한
g′      = gap − 0.5 − (0.2 if 폴백)     보수 보정

g′ ≥ L_min1, 여유 >  0.15  → 🟢 ok
g′ ≥ L_min1, 여유 ≤  0.15  → 🟡 warn (boundary)
L_prac ≤ g′ < L_min1       → 🟡 warn (maneuver)
g′ < L_prac                → 🔴 bad
```

신뢰도는 **측정 품질만** 본다. 판정이 얼마나 아슬아슬한지는 별개 값이다.

```
fit_score = 100 × path_factor × quality_factor
                × (0.5·S_edge + 0.3·S_focal + 0.2·S_agreement)

S_edge      = clamp(1 − patch_sigma_max / 0.5)
S_focal     = 1.0 (exif/api) | 0.6 (26 mm 폴백)
S_agreement = clamp(1 − 세_기준_최대편차 / 0.8)     값이 하나뿐이면 0.7 (중립)

path_factor    = 어느 경로로 쟀는가 (위 표)
quality_factor = 사진이 재기에 적합했는가 — 경고마다 곱한다
                 LOW_MASK_FILL 0.85 · NOT_PARALLEL 0.75
                 HIGH_SIGMA 0.70 · ENDPOINT_PROFILE_UNRELIABLE 0.70

margin_confidence = clamp(min(|g′−L_min1|, |g′−L_prac|) / 0.5)   ← 별도 필드
```

예전엔 판정 여유가 `fit_score` 에 섞여 있어서, **측정이 완벽해도 경계 근처면 점수가
깎였다.** 사용자가 재촬영해도 나아지지 않는 점수였다. 이제 여유가 0.30 미만이면
점수를 깎는 대신 프론트에 `경계에 가까운 판정입니다` 문구를 띄운다.

**이 수식은 `backend/geometry.py` 와 `frontend/index.html` 의
`===LOGIC_START===` 블록에 이중 구현돼 있다.** 한쪽만 고치면
`tests/test_all.py` 의 Python↔JS 교차검증이 깨진다. 반드시 함께 고칠 것.

## Metric3D 를 띄우며 밟은 지뢰 두 개

둘 다 `backend/metric3d_compat.py` 에서 처리하며, **모델·가중치·수식은 손대지 않는다.**
(§11 이 금지하는 "다른 깊이 모델로 갈아타기" 와는 다른 이야기다.)

### 1. `ModuleNotFoundError: No module named 'mmcv'`

Metric3D 의 `mono/utils/comm.py` 가 mmcv 1.x 경로를 쓴다:

```python
from mmcv.utils import collect_env, get_git_hash   # 환경 로깅용, 추론과 무관
```

**`pip install mmcv` 로 해결되지 않는다:**

- mmcv **2.x** 는 저 심볼들을 mmengine 으로 옮기고 삭제했다 → 설치해도 같은 에러
- mmcv **1.x** 는 torch 2.x / Windows 휠이 없다 → 소스 빌드 필요

두 함수 모두 mmengine 에 그대로 있으므로, mmcv 가 없을 때만 최소 shim 을
`sys.modules` 에 등록한다. 진짜 mmcv 가 있으면 **항상 그쪽이 우선**이고,
shim 이 켜지면 WARNING 로그 + `/health` 의 `metric3d_mmcv_shim: true` 로 드러난다.

### 2. `AssertionError: Torch not compiled with CUDA enabled` (CPU 환경)

디코더가 깊이 bin 텐서를 만들 때 device 를 못박아 뒀다:

```python
# RAFTDepthNormalDPTDecoder5.py:795
depth_bins_vec = torch.linspace(..., device="cuda")
```

CPU 로 돌릴 때 이 한 곳만 실제 device 로 교정한다.
(같은 파일의 `create_mesh_grid` 도 기본 인자가 `"cuda"` 지만 호출되지 않는 죽은 코드고,
`ViT_DINO` 의 `.cuda()` 는 xformers 분기 안이라 실행되지 않는다.)
수식 `exp(linspace(log(min), log(max), n))` 은 그대로이므로 **깊이 값은 달라지지 않는다.**

검증된 실측치 (CPU, torch 2.13+cpu):

| | |
|---|---|
| Metric3D 로드 (캐시 후) | ~8 초 |
| 깊이 추론 1장 | ~6~7 초 |
| 전체 `/analyze` | ~10 초 → **프론트 12초 타임아웃 안쪽** |

GPU 가 있으면 자동으로 `cuda` 를 쓰고 교정 로직은 건너뛴다.

`cars_review.csv` 의 **테슬라 모델3 초기형** 행은 `1회진입최소길이` 가 `5.96` 으로

`tools/build_cars_json.py` 의 `KNOWN_REF_DISCREPANCY` 에 사유가 기록돼 있다.
